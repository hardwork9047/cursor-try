# ローカルLLM 同時リクエスト測定

このキットは Web デモではなく、`tools/llm-concurrency-bench/` にある Python の CLI です。GitHub Pages には載せず、ギャラリーのカードからこの README とソースへリンクします。

同じ瞬間に 1 本、2 本、4 本、8 本のリクエストをローカルの LLM サーバへ送り、**先頭トークンまでの待ち時間**がどう伸びるかを測ります。生産現場でいう待ち行列と仕掛品の話です。サーバが一度にさばける数を超えると、あふれた仕事は処理中のまま列に残り、次の先頭トークンが遅くなります。

図は、その実行で測った数値だけから描きます。このフォルダにサンプルの JSON や PNG は入っていません。

## 何を測るか

各同時数について、次を記録します。

- **TTFT（先頭トークンまでの時間）**: そのリクエストの送信開始から、ストリームの最初の非空トークンまで。サーバの中で順番を待った時間も入ります。
- **総時間**: 送信開始から、その応答が終わるまで。
- **生成トークン数**: サーバが返した数。クライアントで文字数から推測しません。
- **デコード速度**: Ollama が `eval_duration` を返したときは `eval_count / eval_duration`。無いときは `(生成トークン - 1) / (総時間 - TTFT)`。待ち時間は入れません。
- **合計スループット**: その回の生成トークン合計 ÷（最初の送信から、最後の応答が終わるまでの秒）。待ちと入力処理を含みます。

同時数ごとに、TTFT の最小・中央値・95%点・最大と、合計スループットの中央値を出します。百分位は線形補間です。標本が 1 件のときは中央値も 95%点も最大も同じ値になります。95%点を安定させるには `--repeats` を増やします。

測る前にウォームアップを 1 回送ります。モデルの読込時間はここに入り、図とレベル集計には入れません。Ollama が `load_duration` を返したときは、その秒数も別に残します。すでに載っているモデルなら、読込はほぼ 0 秒です。

各プロンプトの**質問文は固定**です。先頭だけ依頼 ID が違います。llama.cpp 系はプロンプトの共通プレフィックスをキャッシュするため、全文が同じだと 2 本目以降の入力処理が消え、待ちを短く見せます。ID を先頭に置くのは、そのキャッシュで条件が変わるのを防ぐためです。

temperature の既定は 0、seed は 0 です。

## 何を測らないか

2026-10-10 の [TeksEdge の投稿](https://x.com/TeksEdge/status/2108799696408129674) と [Hugging Face の Superfluid 紹介](https://huggingface.co/blog/basecompute/superfluid) にある数字は、次の条件です。

| 項目 | 公開されている条件 |
| --- | --- |
| マシン | 開発者の Apple M5 Pro |
| モデル | Qwen3.8-27B、4bit |
| 仕事 | 8 エージェントが約 7.5k トークンの文書を処理中 |
| 指標 | そのあいだに来たチャットの、先頭トークンまでの時間 |
| 結果 | llama-server 291 秒、Ollama 380 秒、mlx_lm.server 612 秒、Superfluid 1.5 秒 |

このキットの既定は、**同じ瞬間に N 本を撃つ**試験です。8 本が走っているところへ 2 秒後にチャットを割り込ませる試験ではありません。

公式の手順ページ（[superfluid.sh の Benchmarks](https://superfluid.sh/latest/performance/benchmarks)）には、別の近いシナリオも載っています。そちらは M5 Pro の Qwen3-4B、約 6k トークンの 8 本のあと 2 秒でチャット、という条件で、llama-server 67 秒、Ollama 64 秒です。291 秒とは別の測定です。291 秒の入力長・生成長・並列スロット数の内訳は、一次資料に表がありません。このキットはその穴を推測で埋めません。

近づけるときは、同時数 8 の**最大 TTFT**を見てください。スロットが塞がっているあいだの待ちに一番近い数字です。公開値と秒単位で一致することは期待しないでください。

## 必要なもの

- Python 3.10 以上
- 自分の PC で動いているローカル LLM サーバ
- すでに引いてあるモデル

サーバは次のいずれかです。

- **Ollama**（ネイティブ API。既定 `http://127.0.0.1:11434`）
- **OpenAI 互換**: LM Studio（既定 `http://127.0.0.1:1234/v1`）、llama-server / llama.cpp（よくあるのは `http://127.0.0.1:8080/v1`）、vLLM（よくあるのは `http://127.0.0.1:8000/v1`）

GPU は必須ではありません。CPU でも動きますが、待ち時間の数字は GPU の本番とは別物です。

## インストール

キットのフォルダで一度だけです。

Windows（PowerShell）:

```powershell
Set-Location tools\llm-concurrency-bench
python -m pip install -r requirements.txt
```

`python` が無いときは `py -3` に読み替えてください。

Mac / Linux:

```bash
cd tools/llm-concurrency-bench
python3 -m pip install -r requirements.txt
```

[uv](https://docs.astral.sh/uv/) がある場合は、インストールの代わりに次節の `uv run` で依存が入ってから実行されます。

## ワンコマンド

Ollama でモデルを用意します。タグは `ollama list` の名前を使ってください。

```bash
ollama pull qwen3:8b
```

Windows（PowerShell）:

```powershell
python bench.py --backend ollama --model qwen3:8b
```

Mac / Linux:

```bash
python3 bench.py --backend ollama --model qwen3:8b
```

uv:

```bash
uv run python bench.py --backend ollama --model qwen3:8b
```

`--model` を省くと、応答のあったサーバのモデル一覧を出して終了します。勝手にモデルは選びません。

```bash
python bench.py --backend ollama --list-models
```

`--backend` も `--base-url` も省くと、次の順で探します。

1. Ollama `127.0.0.1:11434`
2. LM Studio `127.0.0.1:1234`
3. llama-server `127.0.0.1:8080`
4. vLLM `127.0.0.1:8000`

複数が応答したときは Ollama を優先し、残りを表示します。

### ほかのサーバ

LM Studio でモデルをロードし、ローカルサーバを開始してから:

```bash
python bench.py --backend openai --base-url http://127.0.0.1:1234/v1 --model <LM Studio のモデル id>
```

llama-server（待受ポートは起動ログを見てください。例は 8080 ですが、新しいビルドの既定は 9931 のことがあります）:

```bash
llama-server -m model.gguf --host 127.0.0.1 --port 8080
python bench.py --backend openai --base-url http://127.0.0.1:8080/v1 --model < /v1/models の id >
```

vLLM も `--backend openai --base-url` です。末尾の `/v1` は無くても補います。

API キーが必要なサーバだけ `--api-key` を付けてください。環境変数 `OPENAI_API_KEY` は送りません。ローカルサーバへクラウドのキーが流れないようにするためです。

## 出力

実行したディレクトリの `results/<UTC時刻>/` に出ます。

| ファイル | 内容 |
| --- | --- |
| `results.json` | 環境、サーバ、ウォームアップ、全リクエスト、集計、読み方 |
| `requests.csv` | リクエストごとの TTFT、総時間、トークン、デコード速度 |
| `summary.csv` | 同時数ごとの中央値・95%点・最大・合計スループット |
| `summary.txt` | 末尾に出す日本語サマリと同じ文章 |
| `ttft.png` | 同時リクエスト数と待ち時間。1200×675 |
| `throughput.png` | 同時リクエスト数と合計スループット。1200×675 |

CSV は UTF-8 BOM です。Excel で開いたときに日本語が崩れにくくするためです。

図のタイトルは「同時リクエスト数と待ち時間」です。線は中央値、95%点、最大です。横軸の 1, 2, 4, 8 は等間隔で、比例軸ではありません。フッターにモデル、量子化（取れたとき）、GPU、バックエンド、日付が入ります。日本語は同梱の Noto Sans JP で描きます。フォントが無い環境では、游ゴシック、ヒラギノ、Noto Sans CJK などを順に探します。

図に「待ち行列」「仕掛品」と出るのは、測った比が次のときだけです。

- **待ち行列**: 最大同時数の TTFT 最大が、最小同時数の TTFT 中央値の 2 倍以上
- **仕掛品**: 同時数が 2 倍以上なのに、合計スループットの伸びがその 75% 未満

どちらでもない実行では、その語は使いません。

失敗した同時数は図に載せません。成功した同時数だけ描き、サマリに失敗を書きます。

## 所要時間

既定は同時数 1, 2, 4, 8 を各 3 回、生成上限 512 トークンです。リクエストは 45 本で、上限まで生成すると 23040 トークンです。サーバが 1 本ずつ処理するときは、おおよそ「23040 ÷ 1 秒あたりのトークン数」が下限です。EOS で早く終わると短くなります。

| 1 本の生成速度の目安 | 直列のときの全体の目安 |
| --- | --- |
| 20 トークン/秒（27B 級の一例） | 約 20 分 |
| 30 トークン/秒 | 約 13 分 |
| 40 トークン/秒 | 約 10 分 |
| 80 トークン/秒（8B の速い GPU） | 約 5 分 |

速い GPU の 8B は 10 分より短く終わることがあります。20 分に近づけたいときは `--max-tokens 1024` にしてください。先に形だけ見たいときは `--repeats 1 --max-tokens 128` です。

待ちの絶対値は生成長にほぼ比例します（直列のとき、後ろのリクエストは前の生成が終わるまで先頭トークンが出ません）。比べる相手と `--max-tokens` を揃えてください。

## OLLAMA_NUM_PARALLEL

Ollama は、この値が結果を決めます。

- 公式ドキュメントの既定は **1** です。1 のモデルは同時に 1 本しか生成せず、残りは待ち行列に入ります。同時数 8 の最大 TTFT は、おおよそ 1 本の総時間の数倍になります。合計スループットはほぼ増えません。
- 値を上げると、スロットの数まで同時に生成します。待ちは縮み、1 本あたりのデコードは落ち、合計スループットは増えることが多いです。必要なメモリは `OLLAMA_NUM_PARALLEL × コンテキスト長` に比例します。
- 古い版は、空きメモリを見て 1 か 4 を自動で選ぶことがありました。環境変数が空でも、実効値が 1 とは限りません。

このキットは、クライアントの環境変数と、Linux では ollama プロセスの環境変数を読みます。Windows のアプリ版や別ユーザーのプロセスは見えないことがあります。見えなかったときは、サマリにその旨を出します。`ollama ps` のコンテキスト長も JSON に残します（ウォームアップの後）。

変え方の例（変えたあとはサーバを再起動し、モデルをロードし直します）:

```bash
OLLAMA_NUM_PARALLEL=4 ollama serve
```

Windows（PowerShell）でユーザ環境変数にする例:

```powershell
[System.Environment]::SetEnvironmentVariable("OLLAMA_NUM_PARALLEL", "4", "User")
```

設定したターミナルとは別のプロセスが `ollama serve` していると、そちらの値が使われます。

llama-server の対応する設定は `--parallel`（`-np`）です。`/props` の `total_slots` が取れたときは JSON の `parallel_slots` に残します。

人と数字を比べるときは、モデル、量子化、同時数、最大トークン、temperature、そしてこの並列数を揃えてください。

## 公開条件に近づける

27B の 4bit を載せたうえで:

```bash
python bench.py --backend ollama --model <27Bのタグ> --profile teksedge
```

`teksedge` は次です。

- 同時数 1, 2, 4, 8
- 各 2 回
- temperature 0
- 生成上限 128 トークン
- 入力を約 7500 トークンにする（短い依頼でサーバの入力トークン数を測り、フィラーの回数を決める。ウォームアップの実測が目標から 20% 以上ずれたら、サマリにそう書く。トークン数が返らないときは短文のまま送り、長くしたことにしない）
- 依頼 ID はリクエストごとに違い、プロンプトの先頭に付く

コンテキスト長は、入力と生成を足した分より大きくしてください。足りないとサーバがエラーを返し、その同時数は図に載りません。

公開試験のエージェントが何トークン生成したかは書かれていません。生成が長いほど、後ろの待ちはさらに伸びます。`--max-tokens` で伸ばせます。

llama-server で同じ長さを撃つ例:

```bash
python bench.py --backend openai --base-url http://127.0.0.1:8080/v1 --model <id> --profile teksedge
```

27B で長い入力を直列にさばくと、同時数 8 の最大待ちだけで数分になることがあり、全体は数十分を超えます。

## オプション

| オプション | 意味 |
| --- | --- |
| `--backend ollama\|openai` | 省略時は自動検出 |
| `--base-url` | サーバの URL |
| `--model` | モデル名。省略時は一覧して終了 |
| `--profile default\|teksedge` | 上の二つの組 |
| `--concurrency 1,2,4,8` | 同時数。この順に実行し、図は小さい順 |
| `--repeats 3` | 各同時数の繰り返し |
| `--max-tokens 512` | 生成上限 |
| `--temperature 0` | 0 以外は比較向きではない、と表示する |
| `--seed 0` | サンプリングの種 |
| `--timeout 1800` | 次のチャンクまでの最大待ち秒。長い列の先頭トークンを切らないため大きめ |
| `--prompt-tokens N` | 目標入力トークン。0 で短文 |
| `--prompt` / `--prompt-file` | 質問文の差し替え。依頼 ID は付く |
| `--api-key` | 必要なときだけ |
| `--output-dir` | 出力先 |
| `--list-models` | 一覧だけ |

思考モデルは、Ollama では `think: false`、OpenAI 互換では `chat_template_kwargs.enable_thinking: false` を先に送ります。サーバが 400 を返したら、そのフィールドを外してウォームアップをやり直します。計測中のリクエストはやり直しません。やり直しは待ち時間を壊すためです。思考テキストが先に来たときは、サマリにそう書きます。先頭トークンは、その思考も含みます。

## 図を投稿するとき

`ttft.png` をそのまま使えます。フッターのモデル、GPU、サーバ、日付と、サマリの `OLLAMA_NUM_PARALLEL`（または llama-server のスロット数）を本文に書いてください。並列数が違うと比較になりません。

## サンプル結果は無い

`--demo` のような、サーバ無しで図を出すモードはありません。失敗した回は欠損のまま残し、埋めて描くことはしません。
